## 1. 结论摘要

当前仓库已经具备 Pydantic 模型、6 个 Agent、FastAPI、Streamlit、`asyncio.gather` 编排和预算循环的演示骨架，现有 10 个 pytest 用例全部通过。但现状尚不能作为后续三阶段的可靠基线，主要原因如下：

1. Mock 航班、酒店、活动和天气均使用无种子的全局随机数，同一输入不能稳定复现。
2. `agents/` 内重新实现了一套 Mock 生成逻辑，`tools/` 下的搜索函数没有被 Agent 调用，数据获取层和业务层实际未解耦。
3. 预算调整通过直接修改活动、酒店和航班价格实现，违反“重新选择候选方案”的约束；而且下一轮并行搜索会覆盖这些修改。
4. 达到最大预算调整次数后，即使仍然超预算，状态仍会变成 `COMPLETED`。
5. Agent 异常只写入 `error_messages`，缺失结果在预算汇总时按 0 元处理，可能将失败方案标记为成功。
6. 日期是未校验字符串。非法日期会静默回退为 3 天，结束日期早于开始日期会静默变为 1 天。
7. 金额允许 `Infinity`，城市允许空字符串；人数只有下界，没有合理上界或业务规则。
8. 当前评分权重和预算比例散落在代码中，活动日预算虽被计算但没有参与候选选择。
9. `ParallelExecutor` 向所有 Agent 传入同一可变状态；当前 Mock Agent 内部也没有真实异步等待，因此“并行”只是结构占位。
10. 返回数据没有统一的 `mock`、数据来源、生成时间或免责声明标记。

因此，阶段 0 应先建立“确定性、可验证、失败显式、预算闭环”的工程基线，再进入偏好澄清、天气联动和双方案比较。

### 2.1 当前调用链

```text

PreferenceAgent -> DestinationAgent
        |
        v
ParallelExecutor
  |- FlightAgent   -- 自己生成随机 Mock 航班
```

### 2.3 当前评分与预算规则

- 目的地：预算适配、安全、季节、旅行风格和签证规则均硬编码。
- 航班：价格 50、时长 30、中转 20，预算内额外加 10；候选数据随机。
- 酒店：价格、目标星级、评分、距离混合打分；候选价格带随机噪声。
- 活动：评分加兴趣字符串匹配，再加随机分；计算出的 `daily_budget` 未用于筛选。
- 预算份额：航班单程判断使用总预算 30%，酒店 40%，活动 25%，口径没有集中配置，也没有统一解释。

## 3. 已复现问题与风险分级

### P0：必须在阶段 0 修复

#### 3.1 失败或超预算被标记为成功

- `BudgetAgent` 在重试耗尽时设置 `PlanningState.COMPLETED`。
- `BudgetLoopController` 循环退出后也无条件设置 `COMPLETED`。
- Flight/Hotel/Activity 结果缺失时，预算汇总将其成本视为 0。
- `BaseAgent.run()` 捕获异常后不设置失败状态，`ParallelExecutor` 也无法感知该异常。

实测：注入一个抛出 `RuntimeError("provider unavailable")` 的 Agent 后，最终状态仍为 `completed`，总价为 0，且 `is_within_budget=True`。

#### 3.2 预算调整不是候选重选

`BudgetAgent._apply_adjustments()` 直接按比例修改：

- `Activity.price`
- `Hotel.price_per_night`
- `Flight.price`

这些价格不是来自候选方案，无法追溯，也违反任务书约束。更严重的是，下一轮 `ParallelExecutor` 会重新生成随机结果，覆盖上一轮的价格修改，所以所谓“渐进式降级”没有稳定效果。

#### 3.3 Mock 不确定

相同输入连续运行 5 次，得到 5 个不同总价：

```text
[6280.0, 8008.0, 6108.0, 7311.0, 8038.0]
```

航班号也每次变化，无法做回归测试、前后对比实验或可追溯解释。

### P1：阶段 0 应修复

#### 3.4 输入校验不完整

实测以下输入均被 `UserPreferences` 接受：

```text
budget = Infinity
departure_city = ""
start_date = "bad"
end_date = "bad"
```

非法日期 API 请求返回 200，并生成默认 3 天行程；倒序日期也返回成功并生成 1 天行程。该行为掩盖用户错误。

#### 3.5 数据层与 Agent 层重复

`tools/` 已有更接近 Provider 的搜索函数，但 Flight/Hotel/Activity Agent 各自维护另一套候选数据与随机生成逻辑。未来替换真实服务时无法只替换 Provider。

#### 3.6 共享可变状态和结果覆盖风险

`asyncio.gather` 中的三个 Agent 接收同一个 `TravelPlanState` 并原地写入。当前写入字段不同，尚未稳定复现覆盖，但这种契约无法支持阶段 C 的两个独立目的地方案。

### P2：进入 A/B/C 前建立规则

- 所有评分权重、预算比例、最大重试次数需要集中配置和版本号。
- Mock 结果需要统一的来源和免责声明。
- API 需要显式返回规划状态，不能只用 `within_budget` 间接表达。
- 健康检查中的 Agent 数量目前硬编码为 6，后续增加 WeatherAgent 会失真。
- 文档宣称并行可降低 60% 延迟，但当前没有基准数据支持。

## 5. 阶段 0 目标设计

### 5.1 设计原则

1. 保留现有 FastAPI 路径和已有请求字段，不破坏现有成功请求的对外结构。
2. Provider 只负责获取候选数据，Agent 负责按规则评分和选择，Orchestrator 负责状态与依赖。
3. Mock 候选集对相同规范化输入必须稳定，禁止依赖进程级随机状态。
4. 预算优化只能选择候选集中的另一项或另一组活动，不允许修改候选原价。
5. 结果缺失、Provider 失败和预算不可满足必须进入显式失败状态。
6. 所有评分与调整策略集中配置、带版本号，并有固定 tie-breaker。

### 5.2 目标调用链

```text
API/CLI -> 输入规范化与校验 -> PreferenceAgent -> DestinationAgent
                                             |
                                             v
                          独立只读 PlanningContext
                           |- FlightProvider -> FlightAgentOutput
                           |- HotelProvider  -> HotelAgentOutput
                           `- ActivityProvider -> ActivityAgentOutput
                                             |
                                             v
                              BudgetEvaluator（只计算）
                                             |
                         预算内 -------------+------------- 超预算
                           |                                 |
                       COMPLETED                    AdjustmentPolicy
                                                        |
                                             按候选重选并重新计算
                                                        |
                                      无可行候选 -> FAILED/BUDGET_INFEASIBLE
```

WeatherAgent 及其对 ActivityAgent 的依赖不在本阶段实现；阶段 0 只保证接口可以在阶段 B 插入。

## 6. 数据结构与接口计划

以下名称为阶段 0 的目标契约，实施时可根据现有模型最小化调整，但语义不可弱化。

### 6.1 公共元数据

```python
class DataSourceMeta(BaseModel):
    source_type: Literal["mock"]
    provider: str
    dataset_version: str
    disclaimer: str

class ScoreBreakdown(BaseModel):
    policy_version: str
    factors: dict[str, float]
    total_score: float
```

所有 Mock 候选结果必须带 `source_type="mock"` 和明确免责声明，不能使用“实时”“当前价格”等表述。

### 6.2 Provider 契约

```python
class FlightProvider(Protocol):
    async def search(self, request: FlightSearchRequest) -> FlightCandidates: ...

class HotelProvider(Protocol):
    async def search(self, request: HotelSearchRequest) -> HotelCandidates: ...

class ActivityProvider(Protocol):
    async def search(self, request: ActivitySearchRequest) -> ActivityCandidates: ...
```

Provider 返回候选列表，不决定最终推荐。真实服务以后通过依赖注入替换 Mock Provider，Agent 和编排器不需要改接口。

### 6.3 Agent 契约

每个 Agent 使用明确的输入模型并返回自己的输出模型，编排器负责把输出合并到状态；并行 Agent 不再原地修改共享状态。

最小契约示例：

```python
FlightAgentInput(preferences, destination, selection_constraints)
    -> FlightAgentOutput(candidates, selected_outbound, selected_return,
                         total_cost, score_breakdown, source_meta)

HotelAgentInput(preferences, destination, selection_constraints)
    -> HotelAgentOutput(candidates, selected, total_cost,
                        score_breakdown, source_meta)

ActivityAgentInput(preferences, destination, selection_constraints)
    -> ActivityAgentOutput(day_plans, total_cost,
                           score_breakdown, source_meta)
```

### 6.4 规划终态

阶段 0 保留 `PlanningState.COMPLETED` 和 `FAILED`，并新增结构化失败原因：

```python
class FailureCode(str, Enum):
    INVALID_INPUT = "invalid_input"
    PROVIDER_ERROR = "provider_error"
    MISSING_REQUIRED_RESULT = "missing_required_result"
    BUDGET_INFEASIBLE = "budget_infeasible"
```

只有所有必需结果存在且预算通过时才能设置 `COMPLETED`。预算不可满足应为 `FAILED` + `BUDGET_INFEASIBLE`，同时保留最佳尝试方案供解释，不得伪装为成功。

### 6.5 金额与日期

- 外部 API 继续接收 JSON number，避免破坏已有客户端。
- 拒绝 `NaN`、`Infinity`、非正预算和负价格。
- 金额统一在计算边界按两位小数归一化；阶段 0 不贸然把现有 JSON 数字改成字符串。
- 日期继续接受 `YYYY-MM-DD` 字符串，但必须通过 Pydantic 校验并保证 `end_date > start_date`。
- 城市去除首尾空格后不能为空；人数上限由配置给出并测试。

## 7. 预算闭环实施方案

### 7.1 候选不可变

Provider 返回的候选价格视为不可变事实。预算循环不修改 `price` 或 `price_per_night`，只修改选择约束并重新运行选择逻辑。

### 7.2 确定性调整顺序

默认策略版本 `budget-policy-v1`：

1. 初始选择：按正常评分选最优组合。
2. 第 1 轮：活动侧在兴趣匹配和每日时段完整的前提下，选择成本更低的活动组合。
3. 第 2 轮：酒店侧从候选集中选择下一档更低总价、仍满足最低规则的酒店。
4. 第 3 轮：航班侧从候选组合中选择更低总价方案，可接受更多中转或更长时长。
5. 每轮都从候选原价重新计算总价，记录 `previous_selection`、`new_selection`、`saved_amount` 和 `rule_id`。
6. 没有更便宜候选或第 3 轮后仍超预算，返回 `FAILED/BUDGET_INFEASIBLE`。

调整顺序、权重、最低酒店星级、最大中转次数等进入配置，不散落在 Agent 内。

### 7.3 确定性 Mock

首选固定 fixture 数据和稳定 ID；如确需生成型 Mock，则使用由规范化请求生成的局部 seed，不得使用全局 `random`。排序必须定义稳定 tie-breaker，例如：

```text
score DESC, total_price ASC, stable_candidate_id ASC
```

## 9. 阶段 0 Acceptance Criteria

### AC-0.1 确定性

- 相同规范化输入连续运行至少 20 次，完整结果 JSON 一致。
- 测试顺序或其他请求不会改变该结果。
- 所有候选有稳定 ID、数据集版本和 `mock` 来源标记。

### AC-0.2 严格输入

- 拒绝非法/倒序/同日日期，除非产品明确支持当日游并单独定义规则。
- 拒绝空城市、非有限金额、非正预算、人数越界。
- API 返回可定位字段的 422，不进行静默默认回退。

### AC-0.3 预算闭环

- 每次调整后的推荐项必须来自原始候选集。
- 候选原价在整个流程中保持不变。
- 每轮调整记录规则、前后选择和节省金额。
- 总价严格等于所选航班、酒店、活动的重新汇总值。
- 仍超预算时最终状态为 `FAILED/BUDGET_INFEASIBLE`，绝不为 `COMPLETED`。

### AC-0.4 失败语义

- 任一必需 Provider/Agent 失败或缺少必需结果，Pipeline 不得成功。
- `error_messages` 不是成功/失败判断的唯一载体，必须有结构化状态和错误码。
- API 摘要中能直接识别规划状态。

### AC-0.5 API 兼容

- `/api/health`、`/api/plan`、`/api/plan/full` 路径保留。
- 现有合法请求字段继续可用。
- 现有成功响应字段保留；新增字段采用向后兼容方式。

### AC-0.6 测试与文档

- 原有测试在修正错误语义后通过或被等价、更严格的测试替代。
- 新增单元测试和 API 集成测试全部实际运行。
- 测试报告记录解释器、依赖版本、用例数、耗时和失败数。
- README 明确所有价格和天气均为 Mock，不声称实时。
