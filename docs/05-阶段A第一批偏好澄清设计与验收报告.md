## 3. 数据契约

### 3.1 `PreferencesDraft`

草稿支持：

- `departure_city`
- `budget`
- `start_date`
- `end_date`
- `duration_days`
- `num_travelers`
- `travel_style`
- `pace`
- `interests`

辅助元数据：

- `field_sources`：每个字段的来源，值为 `explicit`、`inferred` 或 `unknown`。
- `field_errors`：Parser 阶段发现的字段错误。
- `ambiguous_fields`：已提及但不能唯一确定的字段。
- `raw_text`：累计原始回答，便于追溯。
- `revision`：每次合并补充回答后递增。

草稿字段默认均为 `None`，不会沿用 `UserPreferences` 的默认人数或默认旅行风格来掩盖缺失信息。空兴趣列表表示用户明确说“没有特别偏好”；`None` 表示尚未提供，两者语义不同。

### 3.2 `ClarificationResult`

返回：

- 当前 `draft`
- `missing_required_fields`
- 按固定字段顺序生成的 `questions`
- `validation_errors`
- `is_complete`

当前必要字段为出发城市、总预算、出发日期、返程日期、准确人数和旅行风格。`duration_days` 可由日期区间推导；`pace` 和 `interests` 为可选信息，但其来源状态仍然保留。

### 3.3 日期语义

统一采用现有 Pipeline 的结束日排除语义：

```text
duration_days = (end_date - start_date).days
活动日期 = [start_date, end_date)
住宿晚数 = duration_days
```

例如 2026-10-01 出发、2026-10-06 返回，对应 5 天活动和 5 晚住宿。

推导规则：

- 出发日期 + 天数 → 推导返程日期。
- 返程日期 + 天数 → 推导出发日期。
- 出发日期 + 返程日期 → 推导天数。
- 三项均明确且不一致 → 保留原输入并要求确认，不静默改写。
- 修改出发日期时保留已有天数并重算推导得到的返程日期；修改返程日期时重算天数。
- 非法显式日期不会被推导值覆盖。

## 4. Parser 设计

`PreferenceParser` 是运行时可检查的异步协议：

```python
async def parse(text: str, *, reference_date: date) -> PreferencesDraft
```

`MockPreferenceParser` 使用固定词典、正则和中文整数转换：

- 识别预定义出发城市表达。
- 支持阿拉伯数字、`万`/`千` 和约定中文数字预算，包括“一万五”。
- 支持准确人数、旅行天数、六类既有 `TravelStyle`、三类节奏和规范化兴趣标签。
- 支持 ISO 日期、中文年月日、日期区间及今天/明天/后天。
- 相对日期必须使用调用方显式传入的 `reference_date`，测试不读取系统当天。
- “国庆”“春节”等没有年份和精确边界的表达只标记歧义。
- 预算区间和人数范围只标记歧义，不擅自取均值、下限或上限。

Parser 不调用真实 LLM、网络或第三方服务。未来 Real Parser 只需实现同一协议，业务澄清逻辑无需迁移到 Provider 或 API 层。

## 5. ClarificationManager 规则

核心接口：

```python
await manager.start(text, reference_date=...)
await manager.clarify(current, answer, reference_date=...)
manager.apply_manual_update(current, updates)
manager.evaluate(draft)
manager.to_user_preferences(result)
```

合并规则：

- 新回答中来源为 `unknown` 的字段不覆盖旧值。
- 新回答中的明确值覆盖对应旧值，其他已确认字段保持不变。
- 新回答解决某字段后，清除该字段原有歧义和旧错误。
- 日期相关字段按上一节规则协调，无法协调时保留错误并继续追问。
- 无法由有限规则解析的回答可通过 `apply_manual_update` 显式补充；不制造猜测值。
- 只有 `is_complete=true` 才能转换成现有 `UserPreferences`。
- 不完整或非法草稿调用转换接口时抛出 `IncompletePreferencesError`。
- `TravelPlanningPipeline.run` 增加运行时类型闸门，草稿不能绕过转换直接进入正式规划。

## 9. 遗留问题

- 规则 Parser 只承诺固定词典和测试语料覆盖，不具备真实 LLM 的同义表达泛化能力。
- 当前不持久化对话会话；调用方需要保存并回传 `ClarificationResult` 或草稿。
- `pace` 已进入独立草稿契约，但现有 `UserPreferences` 尚无对应字段；本批不擅自改变既有规划契约。
- 节假日没有年份、具体日期或用户所在时区时保持歧义，未接入节假日日历。
- 当前金额继续沿用阶段 0 的有限 float 约定；没有在本批引入 Decimal 迁移。
- 未开发正式 API 和 Streamlit 交互，因此本批不能通过公开 HTTP 或 UI 完成澄清会话。
- 当前仍在脏的 `main` 工作树中；提交和分支隔离等待用户授权。

## 10. 阶段 A 第二批接口依赖

第二批 API/Streamlit 集成应直接复用本批服务，不在表现层重复解析或完整性判断：

1. API 请求显式携带 `reference_date`；相对日期不得使用服务端隐式当天。
2. 首轮接口接收自然语言，返回完整 `ClarificationResult`。
3. 后续接口接收上一版草稿及用户回答，返回递增 revision 的新结果；若采用服务端会话存储，应增加并发更新保护。
4. 对 Parser 无法识别的字段提供结构化手动补充接口，字段仍经同一 Pydantic 与 Manager 校验。
5. 只有 `is_complete=true` 时，API 才调用 `to_user_preferences` 并允许进入现有 Pipeline。
6. Streamlit 展示字段来源、错误和追问，不能自行填充默认人数、日期或风格。
7. 需在第二批决定 `pace` 如何向正式规划契约传递；在决策前不得把它静默映射为 `travel_style`。
8. Real Parser 未来实现 `PreferenceParser` 协议，并继续由 `ClarificationManager` 负责业务完整性和最终校验。
