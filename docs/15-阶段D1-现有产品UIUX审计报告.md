# 阶段 D1：现有产品 UI/UX 审计报告

审计日期：2026-09-26<br>
审计范围：当前 Python Streamlit 产品，不修改已验收后端业务逻辑。

## 1. 审计方法与证据

本次结论来自三类证据，而不是仅凭代码猜测：

1. 完整阅读 `python/ui/streamlit_app.py`、偏好会话、HTTP 客户端和现有 AppTest。
2. 实际启动 Streamlit，健康检查返回 HTTP 200；使用本机无头浏览器分别以 1440×1200 和 480×1400 渲染真实首页并检查页面文字。
3. 运行现有全量回归，结果为 `306 passed, 1 warning in 30.47s`；现有测试继续证明多轮澄清、会话隔离、错误恢复、单/双方案和四种比较状态的行为契约。

当前 `streamlit_app.py` 共 1014 行，UI 逻辑、领域对象格式化、页面状态和所有结果展示集中在同一文件。仓库没有独立 CSS、图标、字体或其他 UI 资产，真实页面主要使用 Streamlit 默认视觉样式。

## 3. 真实页面观察

### 3.1 桌面端

- 页面顶部首先显示产品标题、7 Agent 技术描述、输入方式单选，再进入任务表单。
- 首屏中日期基准、重置按钮、自然语言输入和解析按钮均可见，但产品价值和当前任务层级弱于技术标签。
- 页面宽度较大时表单区域横向利用不足，首屏下半部留白明显；进入结果后又会迅速变为很长的密集页面。
- 真实页面使用默认 Streamlit 颜色、字体、圆角和控件，功能可信，但缺乏可识别的旅行产品视觉语言。

### 3.2 480 px 窄屏

- Streamlit 能将日期输入和“重新开始”按钮安全堆叠，未观察到横向溢出。
- 产品标题在两行内占据很大高度；输入模式、Mock 提示、日期、重置、文本框依次堆叠，主要操作需要较多纵向滚动。
- 重置按钮被放大为整行，视觉权重接近主操作；页面缺乏持久的步骤位置和紧凑偏好摘要。

## 4. 已验证的优点

1. **诚实的业务语义。** `COMPLETED`、`BUDGET_INFEASIBLE`、活动/pace 约束无解和 `FAILED` 都有明确文本，不只靠颜色。
2. **后端事实单一来源。** 比较页直接使用 C2 评分和 ExplanationService；天气解释、预算历史也来自后端记录。
3. **安全边界清晰。** 不完整草稿不能确认；编辑偏好会清除旧结果；网络失败保留有效草稿；产品内“选择方案”明确不是预订。
4. **日期语义可见。** 确认卡同时展示出发日、返程日、活动日期范围和住宿晚数。
5. **默认 Streamlit 可访问性基础尚可。** 输入均有标签，键盘焦点和控件语义由框架提供；错误消息包含文字。

## 5. 主要问题与优先级

### P0：任务流程缺少稳定的空间结构

当前所有阶段共用一条不断增长的纵向页面。用户无法持续知道自己正处于“澄清、确认、规划、比较、详情”的哪一步，也没有跨阶段返回与继续的统一规则。

**影响：** 完成功能虽多，但用户需要依靠页面位置记忆流程；结果较长时，上下文丢失明显。

### P0：信息架构把不同层级内容混在一起

自然语言模式按顺序堆叠对话历史、9 字段表格、校验问题、补充输入、确认卡、模式选择和完整结果。比较模式又在同一页面依次显示 A/B/C/D 四块，并在 D 区内嵌每个方案的五个结果 Tab。

**影响：** 同一数据在偏好卡、比较卡和详情中重复出现；用户难以先做“选择”，再按需查看证据和明细。

### P1：视觉层级依赖默认组件

当前没有统一 token、卡片、状态标签、时间轴或费用组件。`st.metric` 同时承载业务状态、金额、酒店和航班，语义与视觉形式过度复用；emoji 作为标题和 Tab 图标，风格不统一。

**影响：** 重要的业务状态、决策结论和普通统计数字看起来相似，产品辨识度不足。

### P1：比较页可扫读性不足

两方案卡片使用连续 `st.metric`，费用、兴趣、pace、天气和综合评价没有共同的行式比较基线。权重、解释、证据表和完整详情紧接在卡片之后，页面很长。

**影响：** 用户能获得全部信息，但难以在 10 秒内回答“为什么推荐、代价是什么、另一套为什么不选”。

### P1：结果详情缺少时间与天气的联合表达

行程按日期列出活动，天气在独立 Tab，预算在另一 Tab。用户需要跨 Tab 建立“当天什么天气、为什么安排这个活动、费用多少”的关系。

**影响：** 后端已经保存的天气决策证据，没有在最自然的每日时间线中呈现。

### P2：加载与错误缺乏一致容器

当前使用 `st.spinner` 表示整体加载，做法是诚实的；但失败提示、重试动作和保留状态说明分散在不同分支。结构化单方案还直接在 Streamlit 进程内运行 Pipeline，而其他路径走 API，加载体验不完全一致。

**影响：** 用户不知道错误发生后哪些数据仍保留，以及下一步应重试、修改还是返回。

### P2：实现维护成本偏高

1014 行单文件同时负责表单、HTTP、会话、格式化和展示。小型视觉改动容易触碰既有业务分支，增加阶段 D 回归风险。

## 6. 不应“优化”掉的约束

- 不能隐藏 Mock 标识或使用“实时”“已预订”等误导词。
- 不能在前端重新计算比较分数、天气规则或预算结果。
- 不可行方案不能为了卡片整齐显示虚假综合分。
- 修改必要偏好后，旧 HMAC 回执、规划和评分必须失效。
- 规划页在没有事件流 API 前，只能展示整体加载状态，不能伪造 Agent 百分比。
- 天气 unavailable、业务不可行、预算无解、程序错误必须继续使用不同状态和恢复动作。

## 7. 审计结论

现有界面的功能与异常语义已经完整，D2 不需要重写业务能力。最小正确方向是：把同一套后端结果重新组织为五步工作台，引入持续偏好摘要、可扫读双方案卡、日期—天气—活动联合时间轴和统一状态组件；同时把现有大文件拆成纯展示组件，保持 API、HMAC、评分、预算与会话隔离规则不变。
