# Multi-Agent Travel Copilot 产品需求文档（PRD）

**版本：** v1.0（Mock MVP）<br>
**文档性质：** 产品需求基线；供需求评审、开发拆解、验收及简历项目复盘使用<br>
**产品名称：** Multi-Agent Travel Copilot——多智能体个性化旅行规划助手<br>
**当前阶段：** 先使用确定性 Mock 数据和规则解析；不调用真实 LLM、机票、酒店或天气 API

> **范围说明：** 本文描述计划开发的产品需求，不代表这些功能已在代码中实现。所有界面价格、评分、天气和活动信息应显著标为模拟数据，禁止将 Mock 效果宣传为真实模型能力或实时预报。

## 1. 产品背景与问题

现有旅行规划 Demo 已包含偏好、目的地、航班、酒店、活动和预算等模块，但存在以下体验与实现问题：

1. 需要用户主动填写结构化参数，难以承接自然语言表达和模糊需求。
2. 航班、酒店和活动的协调以共享上游状态为主，行程暂不根据天气变化主动调整。
3. 默认产出单个目的地方案，缺乏可对比的候选方案及可追溯的推荐依据。
4. 预算降级采用简化的修改价格方式，重新运行 Agent 可能覆盖前一轮调整结果；活动预算也未成为实际筛选约束。

本项目拟在保持原有业务主干的基础上，构建一个可以澄清需求、进行天气感知的行程安排、提供多方案对比，并完成可靠预算检查的旅行规划 Mock MVP。

## 2. 目标用户与核心场景

**目标用户：** 对目的地或活动没有确定方案，希望快速获得可比较旅行计划的个人或小团体出游用户。

**代表性场景：** 用户输入“国庆想和朋友从上海出去玩 5 天，预算一万五，不想太累，喜欢拍照和吃东西”。系统识别已明确的预算、出发地、兴趣和节奏，追问确切日期及人数；完成画像后，为两个候选目的地分别生成预算可核对、天气可解释的旅行方案。

**核心用户价值：** 减少初次填写成本；避免缺失信息被擅自猜测；让活动安排与天气、兴趣和节奏一致；让不同方案的费用和取舍易于比较。

## 3. 产品目标与非目标

### 3.1 本期目标（P0）

- 支持自然语言入口与结构化表单补充；能够澄清必要字段并让用户确认。
- 能基于可靠、固定的 Mock 数据为两处候选目的地生成彼此独立的完整方案。
- 天气信息必须实际影响 ActivityAgent 的候选过滤或评分，并在天气未知时明确降级。
- 预算模块必须按累积约束进行至多三轮调整；不允许直接篡改供应商报价伪装降价。
- 前端展示方案费用明细、每日行程、数据来源标识及有依据的差异说明。
- 保留原有 API 的兼容性，提供可复现的自动化测试。

### 3.2 非目标（本期不做）

- 不保证任意自然语言输入均能正确理解；Mock Parser 仅支持定义清晰的测试语料与规则。
- 不提供实时票价、真实酒店库存、真实天气预报、预订或支付。
- 不宣称已经验证真实 LLM 的理解准确率或在线 API 的性能。
- 不以增加 Agent 数量作为产品成功指标。

## 4. 用户旅程

1. **输入：** 用户通过自然语言输入旅行意图；也可使用结构化字段补充信息。
2. **解析：** 系统抽取已明确的出发地、日期/时长、预算、人数、兴趣、风格和节奏，生成未完成的偏好草稿。
3. **澄清：** 对缺失或冲突的必填信息进行有针对性的追问；用户可以编辑系统抽取结果。
4. **确认：** 所需信息齐备后，用户确认偏好画像。
5. **规划：** 系统得到候选目的地，为每个目的地独立获取航班、酒店和天气数据；天气准备后生成每日活动。
6. **预算：** 汇总价格并检查预算；超预算时进行有限次、可追溯的重新规划；无法满足时明示原因。
7. **对比：** 展示两套方案的费用、活动、天气适配、节奏与兴趣匹配，并说明各项评价依据。
8. **选择：** 用户自行决定更喜欢哪个方案，可查看详细每日行程。

## 5. 功能需求

### FR-A：Preference Clarification（自然语言需求澄清）｜P0

**A-01 自然语言输入：** 接受用户的一段中文旅行描述，并保存原始文本。

**A-02 偏好抽取：** 将明确字段转换为 `PreferencesDraft`：出发城市、总预算、日期、旅行天数、人数、兴趣、风格、节奏；未给出的值保持未知，不根据“和朋友”等措辞擅自补全人数。

**A-03 规则与提供方隔离：** 定义解析器接口 `PreferenceParser`；本期为 `MockPreferenceParser`，未来允许替换为真实 LLM Parser，而不修改澄清业务接口。

**A-04 缺失信息检查：** 至少检查出发城市、有效旅行日期、总预算、人数；对于“国庆”“下周”等相对日期，结合明确的基准日期解析，仍不确定时提问。

**A-05 多轮澄清：** 生成少量有针对性的问题；接收用户补充或修改，正确合并到草稿。已明确且未被用户修改的字段不得丢失。

**A-06 最终确认：** 用户查看并确认画像后，才能生成合法 `UserPreferences` 并进入原有 Pipeline；未识别文本应引导用户手动修改，不得伪装理解成功。

**本期验收：** 在预先标注的固定语料中正确提取明确字段；缺失字段会触发追问；第二轮回答能正确合并；错误日期、负预算等受到校验；端到端能衔接原 Pipeline。记录字段级正确率，但不得将其外推到未测试自然语言。

### FR-B：Weather-aware Activity Planning（天气驱动行程）｜P0

**B-01 天气数据：** WeatherAgent 通过可替换 Weather Provider 获取与目的地、旅行日期相对应的每日天气；当前 Provider 使用日期对应的固定 Mock 数据，包含 `source`、`is_mock`、覆盖日期和数据可用状态。

**B-02 显式依赖：** 对同一目的地，Flight、Hotel、Weather 可并发；Activity 必须在 Weather 完成或天气回退策略已确定后开始。

**B-03 活动元数据：** 活动候选包含类型、时间段、价格、持续时长、室内/室外、天气敏感度及兴趣标签。

**B-04 天气影响：** 雨天或不宜户外天气，应按规则过滤或降权不适宜的室外活动，并保留实际选择原因；用户对户外兴趣强烈时可保留明确标注风险的候选备选项。

**B-05 联合约束：** 活动按上午/下午/晚上时间段分配；综合兴趣匹配、基础评价、天气适宜度与节奏；每日活动成本、时长不得违反明确的硬约束。评分分项应统一量纲、可配置且可追溯。

**B-06 无天气回退：** 缺少可信天气时，采用不宣称天气优化的基础行程规划，同时展示“天气信息不可用”。远期日期不得展示为真实预报。

**本期验收：** 固定晴天与雨天数据触发符合规则且可解释的行程差异；Activity 不早于 Weather 结果准备；预算与时间约束实际执行；超时与数据缺失时不崩溃、不虚构天气结论。

### FR-C：Multi-plan Comparison & Explainability（多方案对比与解释）｜P0

**C-01 候选目的地：** 默认输出两个候选目的地，并为其创建完全独立的规划状态；候选不足时明确告知。

**C-02 完整方案：** 每套方案均包含目的地、航班、酒店、每日活动、天气可用性、费用明细及预算状态。

**C-03 对比维度：** 用一致的计算口径展示预算匹配、兴趣匹配、舒适度及天气适宜度；评分权重作为待验证产品规则集中配置。缺失维度不得随意填零并继续假装完整评分。

**C-04 可解释性：** 保留每个维度的原始输入、分项得分和可追溯依据；通过确定性模板生成比较说明。若未来升级到 LLM，也不得让模型自行编造价格、天气或评分。

**C-05 用户控制权：** 明确显示不同方案取舍，让用户自主选择；提供详细行程查看，不仅显示一个综合分数。

**本期验收：** 双方案数据无交叉污染；相同固定输入与 Mock 数据重复运行结果可复现；费用与明细一致；所有自然语言解释可追溯至真实计算值和 Mock 来源标识。

### FR-D：可靠预算循环与异常处理｜P0（基础能力）

**D-01 全局核算：** 航班费用、酒店费用与活动费用使用统一人数、晚数和币种约定；预算状态须与最终所展示方案的实际费用一致。

**D-02 累积式约束：** 初始规划后若超预算，原则上依次优先重新选择活动、酒店、航班；后续轮次保留前轮约束，不直接给原报价乘折扣。

**D-03 有界循环：** 调整最多三轮，且每轮记录调整约束、实际候选变化、费用差异及失败原因；无可行候选时明确标记“预算无法满足”。

**D-04 错误与部分成功：** 区分成功、部分成功、超预算、数据不可用与执行失败；单个 Agent 异常时不得静默把缺失结果按零费用当成已完成方案。

**本期验收：** 最终费用与展示明细逐项匹配；轮次间约束累积可见；循环可正常停止；超低预算或缺少候选场景均有明确结果，不出现假成功。

### FR-E：交互页面与 API｜P0

- 在 Streamlit 页面提供自然语言输入、澄清对话、画像确认、规划进度、双方案对比及完整行程查看。
- 保留原有 `POST /api/plan` 及 `POST /api/plan/full` 的兼容性；新增偏好解析、澄清和方案对比接口。
- 所有 Mock 数据显著标注为模拟；不展示“实时查询”“真实大模型生成”等误导文案。
- 使用 Swagger UI 手动验收 API 请求体、响应模型、400/422 错误和异常场景。

## 6. 关键数据契约（建议）

- `PreferencesDraft`：允许缺失字段、原始文本、已提取字段、待澄清字段、用户修订记录。
- `UserPreferences`：仅在用户确认且必填字段通过校验后生成；单独保留旅行节奏 `pace`，不与旅行风格混为一谈。
- `DailyWeather` / `WeatherResult`：日期、天气、降雨风险、数据来源、Mock 标记、可用状态。
- `Activity`：兴趣标签、时段、价格、时长、室内/室外、天气敏感度。
- `BudgetAdjustmentConstraints`：分业务累积约束、轮次、调整原因、候选替换记录。
- `TravelPlanState`：针对单个候选目的地的独立业务状态；包含天气与预算结果。
- `PlanComparison`：独立方案列表、评分明细、输入依据、比较说明和数据完整性标记。

具体 Schema 名称和文件布局可在代码审计后微调，但需要在每一阶段实现前冻结本阶段接口。

## 7. 业务流程与异常情况

**主流程：** 输入 → 解析 → 澄清 → 确认 → 生成候选目的地 → 每个目的地的 Flight/Hotel/Weather 并发 → Weather 完成后生成 Activity → 预算检查与有限次重新规划 → 多方案比较 → 用户查看与选择。

**必须覆盖的异常：** 自然语言无法识别、信息矛盾、人数或预算非法、日期不完整、天气缺失、候选活动不足、某业务 Agent 超时、重复提交、候选目的地不足、预算无解。每个异常都需要可理解的产品反馈，而不是空白页面。

## 8. 非功能需求

- **可复现性：** Mock 数据集版本固定；测试随机数固定或消除随机因素。
- **安全性：** 不把真实 API Key 提交到 Git；个人偏好和会话信息不记录敏感数据；不启用未经批准的付费服务。
- **可观察性：** 记录每个阶段输入类型、执行时间、结果状态和错误信息；日志不输出密钥。
- **兼容性：** 原有 API 和现有可用功能保持向后兼容；改动应有回归测试。
- **可替换性：** Parser、Weather Provider 和其他数据源实现接口隔离，支持未来替换。
- **性能表述：** 不根据瞬时 Mock 调用测量宣称真实 API 的并发提速。

## 9. 度量与实验设计

| 功能 | 需记录的度量 | 测量说明 |
|---|---|---|
| A 偏好澄清 | 字段级正确率、缺失识别率、澄清轮数、完成所需交互次数 | 固定标注样例；与手动表单流程对比；Mock 结果不外推到真实 LLM |
| B 天气感知 | 天气冲突数、活动预算超限率、时段/时长约束通过率 | 同样用户画像与活动池，分别使用固定晴雨场景 |
| C 方案对比 | 方案完整率、解释依据覆盖率、评分可复现性、费用一致率 | 两个目的地使用统一条件；单独记录缺失天气等情况 |
| D 预算优化 | 调整成功率、无解识别率、轮次停止正确率、费用对账通过率 | 固定可行/无解样本，不通过直接修改价格制造假成功 |

本期重点是功能正确性与产品原型可用性；实际体验是否改善，后续应增加用户任务测试，记录真实操作而不是只依赖 pytest。

## 10. 开发与验收里程碑

1. **M0 基础审计：** 冻结原始 Baseline、固定 Mock 场景、修复预算循环、补充回归测试。
2. **M1 Preference Clarification：** Parser 接口、Mock 解析、草稿、追问、确认、API 与测试。
3. **M2 天气感知：** WeatherAgent、提供方接口、编排依赖、活动联合约束、异常回退与测试。
4. **M3 多方案对比：** 独立规划状态、统一评分、数据可追溯解释、对比 API 与测试。
5. **M4 前端及项目展示：** 可交互的 Streamlit 演示、完整端到端测试、前后对比实验及产品复盘。

**每一里程碑的退出条件：** 交付代码与设计变更说明；满足已冻结的验收条件；提交实际 pytest 结果及必要的人工验证结果；检查 git diff；所有未完成项和 Mock 限制如实记录。

## 11. 依赖、风险与待确认项

- **解析能力风险：** 本期仅验证有限规则样本，真实 LLM 接入与泛化评估留到下一版本。
- **天气真实性风险：** 本期所有天气均为模拟；远期真实预报不可凭空生成。
- **多方案可比性风险：** 必须固定用户条件、币种与费用口径，避免不公平比较。
- **评分设计风险：** 当前权重为产品设计假设，不宣称已经验证最优；测试关注规则一致性，后续再开展用户偏好实验。
- **范围风险：** 不在一次 Codex 任务中同时开发所有模块；每一阶段须先冻结数据契约再编码。

**阶段 0 评审中需要明确：** 旅行预算到底是全体旅行者合计还是人均预算；入住与离店日期口径；活动价格是否按人计；目的地不足两处的降级方式；当真实天气不可用时的前端文案。所有模块必须使用一致约定。

## 12. 项目验收与展示边界

最终演示应覆盖：自然语言输入 → 系统提问 → 用户补充 → 用户画像确认 → 两个目的地独立规划 → 天气影响活动 → 预算检查/调整 → 双方案对比 → 展示理由。

交付物包括：本 PRD、架构图、数据契约说明、关键技术取舍、Baseline、单元及集成测试结果、可运行的 Mock Demo、前后对比报告，以及可以准确讲述个人贡献的项目复盘。
