# AI 产品经理简历项目经历与演示脚本

## 1. 简历精简版

**Multi-Agent Travel Copilot｜AI 产品设计与工程实践｜Python / FastAPI / Streamlit**

- 将旅行规划 Demo 拆解为偏好澄清、天气与 pace 约束、候选级预算优化、双目的地比较和
  可解释推荐，设计 Pydantic 契约、业务状态及五步用户流程。
- 设计确定性 Mock 实验体系：固定偏好场景支持字段识别 51/51；天气对照中可评价活动冲突

- 建立两套独立 TravelPlanState 与预算候选快照，支持 recommended / tie /
  only_feasible / no_recommendation；固定 7 场景评价证据 30/30、解释及状态识别 7/7。
- 完成 FastAPI、Streamlit AppTest 和真实 Edge 桌面/390×844 验收；明确 Mock、非实时、
  非预订及真人可用性待验证边界。

建议只保留与目标岗位最相关的 2～3 条，并准备解释指标分母、场景定义和限制。

## 2. 30 秒口述版

“我把一个基础多 Agent 旅行规划器改造成了完整的 AI 产品工作台。重点不是接一个大模型接口，
而是解决三件产品问题：需求不完整时怎么追问，天气和旅行节奏怎么真实改变活动，以及两个
方案怎么在硬约束下做可追溯比较。我用固定 Mock 和版本化规则保证结果可复现，再通过 API、
浏览器和对照实验验证收益与代价。当前没有真实用户和实时供应商，因此作品集明确把这些列为
下一步，而不是包装成上线成果。”

## 3. 3～5 分钟演示脚本

### 0:00–0:35 背景与边界

打开需求输入页，指出“示例 Mock 数据”和“不代表预订”。说明当前 Parser、天气、价格和
库存均为确定性 Mock，演示目标是产品流程和工程契约，不是真实旅行报价。

话术：“原版本要求填表、天气不影响活动、只给一个方案。我按偏好澄清、天气规划和双方案
解释三个阶段改造，并先补齐预算和失败边界。”

### 0:35–1:30 自然语言与澄清

输入：“国庆想和朋友从上海出去玩五天，预算一万五，不想太累，喜欢拍照和吃东西。”

指出系统只提取上海、15000、五天、relaxed、摄影和美食；日期、人数、风格继续追问。补充：
“我们一共3人，2026年10月1日出发，舒适游。”

在确认页展示出发 10 月 1 日、返程 10 月 6 日、活动到 10 月 5 日、住宿 5 晚，并解释 HMAC
回执防止客户端静默篡改。

### 1:30–2:30 天气、pace 与预算

选择双方案并生成。在一个方案详情中展示每日天气、早中晚活动、relaxed 休息时段和天气理由。

话术：“活动不是看到‘下雨’就全部禁止室外，而是先检查硬约束再做软评分。预算超限时也不
直接打折，而是从固定 candidate_id 候选中依次重选活动、酒店和航班，历史可以对账。”

如时间允许，展示固定晴/雨证据：晴天费用 1550、雨天 1910，候选 ID 变化；同时说明这可能
提高费用，恶劣天气没有合规候选时会明确无解。

### 2:30–3:35 双方案与解释

返回比较页，展示两套独立状态、费用、预算余量和四维评价。指出推荐来自 plan-scoring-v1，
前端不重算。

话术：“可行与不可行先于总分。系统允许并列、仅一套可行或不推荐。解释引用真实费用、活动
统计和候选证据；一个权重敏感场景中，预算和兴趣各调整 5 个百分点会从推荐变为并列，所以
页面必须披露敏感性。”

### 3:35–4:15 异常与恢复

展示预算不可满足或天气 unavailable：强调预算状态不等于 Agent 故障、天气未知不等于晴天。
说明网络失败保留已确认偏好；修改偏好后旧评分立即失效。

### 4:15–5:00 结果与复盘

用三组数字收尾：支持字段 51/51；天气冲突 33/63 降至 0/60；双方案评价证据 30/30。
立即补充边界：“这些是固定 Mock 自动化实验，不是真实 LLM 准确率或用户满意度。下一步先做
3～5 人可用性测试，再接真实服务 sandbox。”

## 4. 面试追问准备

**为什么不直接接 LLM？**<br>
先建立数据契约、错误边界和可复现基线，避免把模型随机性与业务逻辑问题混在一起。Parser
Protocol 已保留替换入口。

**为什么天气优化后兴趣匹配下降？**<br>
硬天气约束减少可选活动。在固定候选池中，安全合规与兴趣、费用存在真实取舍；产品应该展示
代价并扩充候选，而不是改指标或伪造活动。

**为什么费用低不一定分高？**<br>
预算匹配评价的是与用户预算的合理匹配，不鼓励单纯牺牲质量求最低价；而超预算会先失去正常
推荐资格。

**为什么需要 no_recommendation？**<br>
数据不足、共同可评价维度不足或两套都不可行时，强行排名会制造虚假确定性。展示已知事实比
给一个没有证据的答案更可信。

**项目最大限制是什么？**<br>
没有真实 Provider、开放域 LLM 和真人研究数据。当前结果证明规则、契约和产品链路可用，不
证明生产市场准确性和用户价值。
