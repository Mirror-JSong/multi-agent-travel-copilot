## 3. 端到端架构

### 3.1 改造前

```text
自然语言 -> parse -> clarify -> 完整 PreferencesDraft -> 仅展示确认卡
结构化表单 ---------------------------------------------> TravelPlanningPipeline
```

### 3.2 改造后

```text
自然语言
  -> POST /api/preferences/parse
  -> POST /api/preferences/clarify（0..n 次）
  -> 完整 PreferencesDraft + HMAC draft_receipt
  -> 用户显式确认
  -> POST /api/preferences/plan
       1. 验证 receipt、reference_date 和 parser config
       2. 服务端重新 evaluate，不信任客户端完成标志
       3. 校验 confirmed
       4. 转换为现有 UserPreferences
       5. 调用现有 TravelPlanningPipeline
  -> TravelPlanState
  -> Streamlit 复用预算结果组件展示
```

结构化入口继续直接调用原有 Pipeline。两个入口没有复制 `DestinationAgent`、`FlightAgent`、`HotelAgent`、`ActivityAgent`、`BudgetAgent`、BudgetLoop 或 Provider。

Pipeline 会在自己的状态副本内补充默认兴趣。确认接口在调用前使用深拷贝，因此 API 返回的“用户确认偏好快照”不会被 Pipeline 内部补充反向污染；`plan.preferences` 仍保持现有 Pipeline 行为。

## 4. 新接口契约

### 4.1 `POST /api/preferences/plan`

请求模型 `PreferencePlanRequest`：

| 字段 | 类型 | 约束 |
|---|---|---|
| `draft` | `PreferencesDraft` | 完整 Pydantic 草稿，禁止未知字段 |
| `draft_receipt` | `str` | 64 位十六进制 HMAC 回执 |
| `confirmed` | `bool` | 必须显式为 `true` |
| `reference_date` | `date` | 必须与签名上下文一致 |
| `config` | `PreferenceParserConfig` | 必须与签名上下文一致，仅允许当前 Mock 版本 |

执行边界：

1. 草稿、字段来源、日期基准或配置被修改，旧回执返回 HTTP 422。
2. 草稿不完整或领域校验失败，返回 HTTP 422 和结构化的缺失字段、校验错误及追问。
3. 草稿完整但 `confirmed=false`，返回 HTTP 409 `confirmation_required`。
4. 验证成功后返回 HTTP 200；规划业务终态保存在 `plan.state`。

响应模型 `ConfirmedPreferencePlanResponse`：

- `confirmation_accepted`：服务端接受了本次确认动作。
- `preferences`：服务端由签名草稿转换的确认快照。
- `draft`：已验证草稿。
- `draft_only_fields`：当前为可选的 `pace`；它没有进入 `UserPreferences`。
- `plan`：原有完整 `TravelPlanState`，包含候选快照、推荐结果、费用、调整历史和失败信息。
- `is_mock`：当前为 `true`。
- `identity_notice`：明确确认动作不能证明特定自然人的身份。

HMAC 密钥不进入响应或日志。无数据库、账户或身份认证，因此该机制只证明服务端签发后内容未被修改，不提供用户身份归属证明。多 Worker 部署必须配置相同的私密 `PREFERENCE_DRAFT_SIGNING_KEY`。

## 5. Streamlit 产品流程

自然语言模式现在支持：

1. 输入旅行需求并调用 `/parse`。
2. 展示识别字段、来源、校验错误与追问。
3. 多轮调用 `/clarify`，更新签名草稿。
4. 展示出发日、返程日、活动范围和住宿晚数。
5. 由用户主动点击“确认并生成旅行方案”。
6. 显示加载状态并调用 `/plan`。
7. 复用阶段 0 预算组件展示目的地、航班、酒店、每日活动、费用和调整历史。

信息不完整时确认按钮禁用；修改字段会清除旧规划与确认状态；规划中及已获得结果后按钮禁用，避免同一页面重复提交。连接失败或超时时保留有效草稿，允许重试。`BUDGET_INFEASIBLE` 和 `FAILED` 使用不同提示，失败不会显示为成功。

结构化表单模式继续保留并通过回归。`pace` 仅显示为草稿字段，界面明确说明它尚未影响 ActivityAgent。

## 11. 已知限制与风险

1. Parser 是有限中文规则和词典，不具备真实 LLM 的开放域理解能力。
2. Mock 航班、酒店、活动不是实时库存或价格，不能用于预订。
3. `pace` 仍只在草稿中保存和展示，尚未进入 `UserPreferences` 或 ActivityAgent。
4. HMAC 默认密钥在进程启动时随机生成；生产式多 Worker 或重启续聊必须显式配置共享私密密钥。
5. 无用户身份、数据库或跨设备会话；客户端确认只是一项请求动作。
6. `BUDGET_INFEASIBLE` 只说明当前三阶段启发式搜索没有找到预算内方案，不证明所有候选组合数学无解。
7. 金额当前保持阶段 0 的两位小数归一化方案，整体迁移 `Decimal` 仍是后续技术优化。
8. 当前单目的地请求已做状态深拷贝与会话隔离；阶段 C 双方案必须为每个候选目的地建立独立 `TravelPlanState`，不能共享可变状态。
9. 第三方 Starlette/AnyIO 弃用 warning 尚未消除，等待依赖兼容升级。
