## 3. 正式网页架构

```text
streamlit_app.py                 页面编排，不计算业务分数
├─ preference_api_client.py      单方案/双方案/澄清 HTTP 客户端
├─ preference_session.py         签名草稿、日期基准和对话会话状态
├─ workbench_state.py            五步工作台状态与失效规则
├─ theme.py                      本地视觉 token、卡片、时间轴和窄屏规则
└─ components/
   ├─ navigation.py              五步导航和页头
   ├─ preferences.py             对话、字段来源、偏好摘要与确认卡
   ├─ status.py                  真实整体 Loading 和可重试错误
   ├─ comparison.py              C2 服务端评价、解释和可追溯证据的只读展示
   └─ plan_result.py              天气、行程、休息、交通、酒店、预算及故障展示
```

API Client 负责请求、超时和响应契约；页面组件只消费后端结果。预算、天气、
pace 和 C2 评分均没有在 Streamlit 中重新实现。

## 4. 五个界面与 D1 对照

| D1 目标 | D2 实现 | 真实数据来源 |
|---|---|---|
| 旅行需求与 AI 对话 | 左侧导航、澄清对话、右侧字段来源摘要；保留结构化入口 | `/api/preferences/parse` 和 `/clarify` |
| 偏好确认与配置 | 显示出发/返程/活动日期、住宿晚数、pace、预算及单/双方案 | 签名 `PreferencesDraft` 和服务端重新校验 |
| 规划执行 | 请求先进入独立第 3 步再执行；只显示整体进行中 | 同一个 FastAPI 请求，无伪进度 |
| 双方案比较 | 并列卡、四维评价、有效权重、证据、解释和敏感性提示 | `MultiPlanResult` + `PlanComparisonResult` |
| 每日行程与预算 | 方案切换、天气、三时段/休息、强度、交通、酒店、费用和调整历史 | 已有独立 `TravelPlanState` |

与 D1 的差异：Streamlit 窄屏时使用自带可折叠侧边栏，而不是原型中自定义底部
导航；浏览器会显示 Streamlit 自带的 Deploy/菜单区域。这两项是为了保持稳定、键盘
可达的原生组件，没有依赖易变的内部 DOM 结构强行隐藏。

## 5. Session State 契约

| 状态类别 | 主要字段 | 失效/保留规则 |
|---|---|---|
| 页面 | `ui_step`, `ui_last_step`, `ui_input_mode` | 只允许 intake/confirmation/planning/comparison/detail |
| 澄清 | `preference_response`, `preference_history`, `preference_reference_date_locked` | 日期基准在签名会话内锁定 |
| 确认 | `preference_confirmed`, `confirmed_preferences_fingerprint` | 修改必要偏好立即取消确认 |
| 请求 | `planning_request_state`, `pending_planning_request` | 单次排队，第 3 步执行，结束后清空 |
| 结果 | 自然语言/结构化单方案与比较结果 | 修改对应偏好时一并失效，不混用旧分数 |
| 查看 | `active_plan_id`, `active_detail_tab` | 切换方案只读现有结果，不重跑 Pipeline |
| 错误 | `ui_last_error`, `ui_last_warning` | 网络失败保留有效偏好和输入，允许安全重试 |

Streamlit `session_state` 由每个浏览器会话独立管理；没有全局客户端草稿。HMAC
密钥只在 FastAPI 服务端，未写入会话、页面或日志。

## 6. 异常和特殊状态验收

真实 Uvicorn 受控 Mock 端点返回：

| 场景 | HTTP | 规划状态 | 天气状态 | 关键证据 |
|---|---:|---|---|---|
| 天气不可用 | 200 | `completed` | `unavailable` | 基础规划回退，不显示为晴天 |
| 天气活动无解 | 200 | `activity_constraints_unsatisfied` | `ready` | 不编造活动 |
| 极低预算 | 200 | `budget_infeasible` | `ready` | 3 轮调整历史 |
| WeatherProvider 超时 | 200 | `completed` | `degraded_timeout` | 显式降级，与程序故障区分 |
| 必要 FlightAgent 故障 | 200 | `failed` | `ready` | 1 条结构化 Agent failure，无伪成功预算 |

比较页通过固定 C2 Fixture 与 AppTest 实际验证 `tie`、`only_feasible` 和
`no_recommendation`；正常服务浏览器演示返回 `recommended`。不可行方案的
`overall_score` 保持空值，没有为对齐卡片填入假分数。

## 10. 已知限制

- Streamlit 没有后端细粒度进度事件，因此只能诚实展示整体请求进行中。
- 窄屏下侧边导航收起，对比卡片纵向排列；这是 Streamlit 的现实边界。
- 会话只在当前浏览器连接中保留，无账户、数据库或跨设备续聊。
- 所有价格、天气、候选、时长和强度仍是版本化 Mock 数据，无真实预订能力。
- D2 是工程与服务级验收，没有产生或宣称真人满意度、完成时长改善或可用性结论。

## 11. D3 最终产品验收建议

1. 在建立用户授权的 Git 检查点后，用独立 D3 分支执行。
2. 以 5–8 位目标用户执行固定任务脚本，分开记录任务成功、误解、放弃点和主观反馈。
3. 真人测试前冻结 Mock 版本、评分策略、语料和浏览器视口，不用中途改数据获取更好结果。
4. 验证读屏顺序、Tab/回车键、对比度、放大比例和手机真机；AppTest 不能替代这部分。
5. 分别记录正常、并列、仅一套可行、无法推荐、网络失败和业务不可行的用户理解。
6. 只能用真实任务记录计算成功率和耗时，不将自动化脚本点击数据伪装成用户体验改善。
