## 3. 最终架构与数据流

```text
结构化 UserPreferences ───────────────────────────────────────────────┐
                                                                    │
签名 PreferencesDraft → HMAC/上下文/完整性/确认校验 → UserPreferences ┤
                                                                    ▼
                                             PlanComparisonApplicationService
                                                                    │
                                                  ComparisonOrchestrator（C1）
                                                                    │ 一次规划
                                                        MultiPlanResult
                                                         ├─ 方案 A 独立 State
                                                         └─ 方案 B 独立 State
                                                                    │ 同一只读输入
                                      ┌─────────────────────────────┴──────────┐
                                      ▼                                        ▼
                       PlanComparator / ExplanationService        替代权重敏感性检查
                                      │                                        │
                                      └─────────────────────────────┬──────────┘
                                                                    ▼
                                                    PlanComparisonApiResponse
                                                                    ▼
                                          FastAPI → Streamlit（只展示，不重算）
```

`PlanComparisonApplicationService` 每次请求创建新的 `ComparisonOrchestrator`，并深拷贝
偏好和配置；两个 comparator 读取同一个 C1 结果。C2 的输入指纹包含评分策略版本，因此
C3 的 `same_planning_input` 依据应用服务的一次规划事实记录，而不是错误地比较两个策略
指纹。

## 4. API 契约

### 4.1 `POST /api/plans/compare`

请求模型为既有 `MultiPlanRequest`：

- `preferences: UserPreferences`
- `plan_count: 1..2`，默认 2
- `config: MultiPlanConfig`

额外字段被 Pydantic 拒绝，因此客户端不能提交 `overall_score`、推荐目的地或候选对象
覆盖服务端结果。

### 4.2 `POST /api/preferences/compare`

请求模型为 `ConfirmedPreferenceComparisonRequest`：

- 完整 `PreferencesDraft`
- `draft_receipt`
- `confirmed`
- `reference_date`
- `PreferenceParserConfig`
- 独立 `planning_config`

执行顺序：验证 HMAC → 服务端重新评价完整性与领域约束 → 检查显式确认 → 转换
`UserPreferences` → 调用统一比较服务。客户端伪造 `is_complete`、修改字段来源、日期基准、
Parser 配置或草稿内容均不能复用旧回执。

### 4.3 `PlanComparisonApiResponse`

响应包含：

- `request_status`：`completed / completed_with_issues / no_plans / failed`
- `confirmation_accepted`
- 服务端采用的 `preferences`
- 完整 `MultiPlanResult`
- 完整 `PlanComparisonResult`
- `SensitivityDisclosure`
- `is_mock`、Mock 限制和身份确认限制

HTTP 200 只表示请求被正常处理，不表示两个业务方案都成功。每个方案仍以自己的
`COMPLETED / BUDGET_INFEASIBLE / ACTIVITY_CONSTRAINTS_UNSATISFIED /
PACE_CONSTRAINTS_UNSATISFIED / FAILED` 为准。

## 5. Streamlit 集成

### 5.1 交互

- 自然语言：解析 → 多轮澄清 → 确认卡 → 选择单方案/双方案 → 调用真实 FastAPI。
- 结构化表单：保留原单方案按钮行为，双方案模式通过正式结构化比较 API。
- 修改结构化偏好后，基于规范化 `UserPreferences` 指纹立即清除旧比较结果。
- API 超时或网络错误时保留完整草稿、签名回执、历史和规划模式，允许重试。
- 不同 AppTest 会话拥有各自的草稿与比较结果。

### 5.2 页面区域

1. 偏好摘要：城市、日期、人数、预算、兴趣、风格、pace 和 Mock 标识。
2. 对比卡片：目的地、业务状态、费用/余量、四维评价与综合分。
3. 推荐解释：直接展示 C2 决策、解释、证据、有效权重、局限与敏感性提示。
4. 方案详情：复用已验收的航班、酒店、活动、天气、pace、预算和调整历史组件。

不可行、失败或证据不足方案不显示虚假综合分。用户选择某一方案只是产品内查看选择，
不代表真实预订。
