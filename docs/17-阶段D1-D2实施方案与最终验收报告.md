## 6. 前后端数据映射

| 页面/组件 | 后端事实来源 | 前端规则 |
|---|---|---|
| 对话与偏好摘要 | `/api/preferences/parse`、`/clarify` | 展示值和 field_sources，不自行推断 |
| 确认卡 | `date_summary`、签名 draft | 用户主动确认；修改后旧 receipt 失效 |
| 单方案 | `/api/preferences/plan` 或 `/api/plan/full` | 只格式化 `TravelPlanState` |
| 双方案卡 | `/api/preferences/compare` 或 `/api/plans/compare` | 费用来自各自 `DestinationPlan` |
| 四维评价 | `comparison.plan_evaluations` | `normalized_score=null` 显示不可评价，不填 0 |
| 推荐 | `comparison.recommendation` | 尊重四种正式决策，不按分数自行排序 |
| 敏感性 | `sensitivity` | 原样披露，不自行运行替代评分 |
| 每日天气 | `weather_result`、`weather_planning` | unavailable 不显示晴天 |
| 活动依据 | `weather_decisions`、pace 原因 | 只有真实 change 才写“因天气替换” |
| 预算 | `budget_breakdown`、`adjustment_history` | 不重算折扣，不隐藏费用上升 |
| 故障 | `agent_failures`、`business_issues` | 与业务不可行分开显示 |

## 7. 页面状态管理

建议继续使用每个浏览器独立的 `st.session_state`，增加一个薄的 UI 状态层：

- `ui_step`: `intake / confirmation / planning / comparison / detail`
- `planning_mode`: `single / compare`
- `confirmed_preferences_fingerprint`
- `active_plan_id`
- `active_detail_tab`
- `last_transport_error`

必须复用现有：`preference_response`、`draft_receipt`、`preference_history`、`preference_plan_result`、`preference_comparison_result` 和结构化指纹。

集中实现一个 `invalidate_results(reason)`：偏好、日期基准、Parser 配置或规划配置变化时，清除单方案、比较、选中方案与确认状态；不要清除仍有效的输入和对话历史。
