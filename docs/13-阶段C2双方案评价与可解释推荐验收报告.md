## 3. 架构与数据流

```text
ComparisonOrchestrator（C1，只运行一次）
  -> MultiPlanResult（完整方案、事实和原始请求偏好）
  -> PlanComparator（C2，只读深拷贝）
       -> 业务状态 / 数据完整性闸门
       -> 预算、兴趣、节奏、天气四维事实计算
       -> 双方共同指标与同一有效权重
       -> 综合分或明确的不可比结果
       -> ExplanationService（结构化事实模板）
  -> PlanComparisonResult
```

`PlanComparator` 不重新查询 Provider、不重新运行 Pipeline、不重新生成候选，也不修改 `TravelPlanState`。输入在评价前后进行 JSON 指纹校验；评价结果与原方案使用独立对象。

为避免把 `PreferenceAgent` 的兼容默认兴趣误认为用户明确偏好，`MultiPlanResult` 向后兼容地增加了可选 `request_preferences`。C1 编排器保存进入流程前、已验证的原始 `UserPreferences` 深拷贝；旧的序列化结果缺少该字段时仍可读取，但兴趣和 pace 会因证据不足而禁止正常评价。

串行/并发是执行策略而非业务事实，评价输入指纹明确排除 `execution_mode`，因此相同业务方案获得相同评价 ID 和结果。

## 4. 数据契约

### 4.1 核心模型

- `MetricEvaluation`：指标名、原始值、0～100 规范化分、分子、分母、评价状态、配置权重、有效权重、证据和限制。
- `PlanEvaluation`：目的地、原规划状态、评价资格、四项指标、综合分、策略版本、数据完整性和限制。
- `PlanComparisonResult`：双方评价、指标差异、可比性、共同指标、实际权重、推荐、解释、来源版本和限制。
- `MetricEvidence`：稳定字段路径、规范 JSON 值、候选 ID 和证据说明。
- `ScoringPolicy`：所有权重、阈值和 pace 参数的集中、严格校验、不可变配置。

### 4.2 状态语义

- 指标状态：`evaluated`、`not_applicable`、`partial`、`insufficient_data`、`ineligible`。
- 方案评价资格：`eligible`、`business_infeasible`、`failed`、`insufficient_data`。
- 双方可比性：`comparable`、`single_feasible`、`not_comparable`。
- 推荐决策：`recommended`、`tie`、`only_feasible`、`no_recommendation`。

## 5. C1 字段到 C2 指标的映射

| 指标 | 真实输入字段 | 分子 / 分母 | 空值与禁止计算 | 主要证据 |
|---|---|---|---|---|
| 预算匹配 | `budget`、`final_total_cost`、`within_budget`、规划状态 | 预算余量 / 用户预算 | 非 `COMPLETED` 不生成正常分；费用或合规标记缺失、状态矛盾时证据不足 | 预算、最终费用、原业务状态 |
| 兴趣匹配 | 原始 `request_preferences.interests`、实际入选 `activity_facts.matched_interests` | 匹配活动数 / 可评价活动数 | 未声明兴趣为不适用；休息不进分母；没有活动时证据不足 | 兴趣、候选 ID、匹配计数 |
| 节奏适配 | 原始 pace、每日活动数、强度、时长、休息、`pace_compatible` | 按 pace 规则计算 | 未声明 pace 为不适用；需要属性但未知时证据不足 | 每日明细、候选 ID、休息与属性状态 |
| 天气适宜度 | `weather_result`、`weather_planning`、实际活动 `weather_compatible` | 天气合规活动数 / 可评价活动数 | unavailable 不计 0 分；partial 或活动评价不全不生成完整分；没有活动时证据不足 | 天气状态、活动候选 ID、合规计数 |

## 6. 四维公式与策略版本

默认策略版本：`plan-scoring-v1`。

默认配置权重：

- 预算匹配：30%。
- 兴趣匹配：30%。
- 节奏适配：25%。
- 天气适宜度：15%。

### 6.1 预算匹配

设 `r = (预算 - 最终费用) / 预算`。仅完整、预算内方案计算：

`score = 80 + 20 * min(max(r, 0) / 0.20, 1)`

预算刚好用尽为 80 分，余量达到 20% 为 100 分并封顶。因此便宜到一定程度不会继续被自动解释为更优。

### 6.2 兴趣匹配

`score = 匹配用户声明兴趣的实际入选活动数 / 实际入选活动数 * 100`

休息时段不进入分子或分母。没有声明兴趣时为 `not_applicable`，不是 0 分。

### 6.3 节奏适配

- `relaxed`：逐日检查 1～2 项活动、至少一个明确休息时段、无 high、已知总时长不超过 5 小时且活动通过 pace 硬约束；得分为通过天数比例。
- `balanced`：保持历史兼容的三时段容量；得分为每天 3 项且无休息占位的天数比例，不主观奖励低强度。
- `packed`：`70% * 三时段容量达成率 + 30% * 强度亲和度`；high/medium/low 亲和度为 1.00/0.75/0.50。high 对明确选择 packed 的用户不是负面属性。

### 6.4 天气适宜度

`score = 通过天气硬约束的实际入选活动数 / 具有天气评价的实际入选活动数 * 100`

不根据晴天、雨天名称额外加分，也不制造城市差异。天气不可用、部分缺失或活动评价不完整时不生成完整天气分。

### 6.5 综合分

先检查双方状态和数据完整性。只有双方 `eligible`，并且使用完全相同的 `evaluated` 指标集合时才计算综合分。双方同时 `not_applicable` 的维度可被排除，其余共同指标按原权重同比例重分配，并在结果中公开 `effective_weights`。

任一方缺失适用指标、两边可评价集合不同，或没有共同指标时返回 `not_comparable`，不强行出分。综合分差不超过 2 分时返回 `tie`。

## 7. 硬约束、缺失数据与推荐

- 只有 `COMPLETED` 有正常评价资格。
- `BUDGET_INFEASIBLE`、天气/pace/活动约束不可满足继续保留原业务语义，不能靠其他维度高分恢复推荐资格。
- `FAILED` 的四维指标均为 `ineligible`，不产生普通综合分。
- 一套可行、一套不可行时返回 `only_feasible`；这是可行性条件推荐，不是把不可行方案当作低分方案。
- 缺失指标不自动计为 0。
- 天气不可用不伪造晴天或天气分。
- 未声明兴趣或 pace 为 `not_applicable`，不推断用户偏好。
- 必要证据不足时返回 `no_recommendation`。

## 8. 解释机制与可追溯性

`ExplanationService` 使用确定性的 Python 模板，所有文本来自实际字段或评分结果。支持：

- 精确费用差和两边最终费用。
- 兴趣匹配数量、分母和候选 ID。
- pace 规则、每日统计和属性证据。
- 天气状态、活动适配计数和候选 ID。
- 不可行/失败的原业务状态与原因。
- 并列、仅一套可行、数据不足和条件化推荐。

解释明确说明：城市天气条件下的实际适配差异不是“启用天气优化机制”的因果实验结论。费用更低也不会单独被描述为整体更优。

## 11. 权重敏感性

对演示 A 使用同一份 C1 原始结果，仅把预算权重从 30% 调为 35%、兴趣从 30% 调为 25%，其余不变，版本记为 `plan-scoring-sensitivity-v1`：

- 默认：海城 90，山城 94，推荐山城。
- 调整后：海城 91.6667，山城 93，分差 1.3333，返回并列。

五个百分点的权重转移使结论从推荐变为并列，说明该场景对预算/兴趣权重敏感。报告和原始 JSON 均保留策略版本、权重和双方分数；这不是绝对客观结论，也未为获得预设结果修改候选数据。

## 15. 风险与限制

- 权重、阈值、活动强度和时长均为版本化产品规则及 Mock 属性，未经真人偏好研究验证。
- 兴趣匹配仍是现有确定性字符串规则，不代表真实语义理解或 LLM 泛化能力。
- 预算评分采用“20% 余量封顶”的产品假设；未来若变更必须升级策略版本并重跑敏感性实验。
- 天气硬约束使成功方案常同为 100；系统没有人为制造天气差异。
- 历史 C1 JSON 若无 `request_preferences`，不能可靠区分显式兴趣与兼容默认值，因此相关指标可能证据不足。
- 当前结果仅供规则化比较展示，不是价格、天气或体验的真实市场建议。

## 16. C3 接口依赖

C3 可直接复用：

- 输入：已验证的 `MultiPlanResult`。
- 服务：`PlanComparator(policy).compare(multi_plan_result)`。
- 输出：完整 `PlanComparisonResult`，包括双方指标、有效权重、推荐、解释、证据、数据版本和限制。
- UI 只展示后端产生的解释和证据，不应在前端重新计算评分。
- 正式 API 应使用明确 Pydantic 请求/响应模型，并在服务端运行 C1 编排和 C2 比较；不得信任客户端提交的分数或推荐。
- `single_feasible`、`not_comparable`、`tie` 和 `no_recommendation` 必须作为正常业务结果展示，而不是 HTTP 500。
- C3 应继续保持单方案 API 兼容，并测试不同浏览器会话的双方案结果隔离。

阶段 C2 到此停止；未开发 C3 API、C3 Streamlit 页面、真实 LLM、真实天气或供应商服务。
