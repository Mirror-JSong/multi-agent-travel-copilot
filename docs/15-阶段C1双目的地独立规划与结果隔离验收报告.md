## 3. Pipeline 审计与最小改造

### 3.1 审计结论

- `DestinationAgent` 从固定目的地目录计算分数，稳定排序后返回前三个候选，并自动选择第一个。
- 原 `TravelPlanningPipeline.run()` 在目的地选择后依次执行：Flight/Hotel/Weather 隔离并行、Activity、BudgetLoop。
- `TravelPlanState` 包含多个可变列表与嵌套模型，包括候选集合、天气结果、活动安排和调整历史，不能供两个方案共享。
- `ParallelExecutor(isolate_state=True)` 已能对同一个方案内的三个并行 Agent 使用深拷贝并按声明字段确定性合并，但它不等于双方案状态隔离。
- Provider 使用请求级稳定摘要和深拷贝返回值，不依赖全局随机状态。
- BudgetOptimizer 固定候选快照并累积修改当前选择；不同目的地必须拥有不同快照。

### 3.2 最小改造

保留原单方案 `run()`，仅抽取目的地选择后的私有执行段：

```text
_run_selected_destination_state(state)
    → Flight + Hotel + Weather（隔离并行）
    → Activity（等待天气状态）
    → BudgetLoop（固定候选快照）
```

新增公共入口：

```python
await pipeline.run_for_destination(preferences, destination)
```

该入口校验 `UserPreferences` 和 `Destination`，深拷贝两者，显式设置 `DestinationRecommendation.selected`，不调用 `DestinationAgent`。原 `run()` 和新入口最终进入同一个后目的地执行函数，因此没有复制 Agent、Provider、天气规则或预算算法。

原单方案请求的规范化业务结果专项测试保持一致。Pipeline 现在也对原单方案输入偏好做深拷贝，避免 `PreferenceAgent` 的默认兴趣补充反向修改调用方对象；实际规划输出不变。

## 4. C1 数据契约

契约位于 `python/models/multi_plan.py`，均使用 Pydantic v2 且 `extra="forbid"`。

### 4.1 MultiPlanRequest

- `preferences: UserPreferences`
- `plan_count: 1..2`，MVP 默认 2
- `config: MultiPlanConfig`
  - `execution_mode: serial | concurrent`
  - `max_concurrency: 1..2`
  - `activity_planning_mode`
  - `weather_scenario`
  - Flight/Hotel/Weather Mock 数据版本
  - Activity Mock 数据版本
  - Destination 数据版本

### 4.2 DestinationPlan

- 稳定 `destination_id`
- 完整 `Destination`
- 独立完整 `TravelPlanState`
- 原业务 `PlanningState`
- `execution_completed`
- `errors: list[AgentFailure]`
- `business_issues`，与程序故障分开
- `comparison_data`，只保存可追溯事实

模型验证内部 `plan.state` 与外层状态一致，并验证内部 `selected_destination` 与外层目的地一致。

### 4.3 MultiPlanResult

- 稳定 `request_id`
- 完整目的地候选摘要、排名、选择依据与数据版本
- 各目的地独立方案
- 请求、选择、生成、成功、失败/不可行数量
- `orchestration_completed`
- 编排问题列表

`successful_plan_count` 只统计 `COMPLETED`。`BUDGET_INFEASIBLE`、`ACTIVITY_CONSTRAINTS_UNSATISFIED`、`PACE_CONSTRAINTS_UNSATISFIED` 和 `FAILED` 均保留原义，不合并成一种结果。

`orchestration_completed=true` 表示候选发现和所有已选择目的地的执行已经得到确定结果，不表示全部方案成功。DestinationAgent 程序故障时该字段为 false；只有一个/没有有效候选是正常编排结果，因此为 true，并通过结构化 issue 说明。

### 4.4 C2 事实数据

`PlanComparisonData` 提供：

- 最终总费用及 Flight/Hotel/Activity 明细
- 预算合规与调整轮次/历史数量
- 每日活动数
- 每项活动的候选 ID、兴趣匹配标签、天气/pace 兼容性、强度、时长和来源状态
- 明确休息时段及原因
- CandidateSnapshot 是否可用
- Flight、Hotel、Activity、Weather 实际来源版本
- 缺失数据字段列表

没有 `score`、综合排名或胜出推荐。失败方案不会虚构缺失的费用或候选数据。

## 5. ComparisonOrchestrator 执行流程

```text
已验证 UserPreferences（深拷贝）
  → PreferenceAgent
  → DestinationAgent（一次）
  → 按稳定结果过滤非法/重复目的地并选择前 N 个
  → 每个目的地新建 Pipeline + 新建 TravelPlanState
      → run_for_destination
      → Flight / Hotel / Weather
      → Activity
      → BudgetLoop
  → 按候选顺序收集 DestinationPlan
  → MultiPlanResult
```

稳定 ID 使用 SHA-256 规范化输入与数据版本生成，不使用 Python `hash()`。`request_id` 不包含串行/并发实现选项，因此相同业务请求在两种模式下相同；Mock 版本、天气情景或活动模式变化会改变业务身份。

并发通过 `asyncio.Semaphore` 限制为最多 2。`asyncio.gather` 按原候选顺序收集结果。每个任务由 factory 新建全部业务 Agent 与 Provider；没有共享可变 Pipeline 或状态。单目的地意外异常会被转换成该目的地的结构化 `FAILED`，不会取消或覆盖另一方案。

## 10. 已知风险与 C2 启动条件

### 10.1 已知风险

1. C1 只有内部 Python 编排接口；正式 HTTP 数据契约、幂等/限流策略和 Streamlit 比较 UI 尚未实现。
2. `DestinationAgent` 的原始候选尚未内建 candidate_id/source 字段；C1 在编排结果中根据城市、国家和目的地数据版本生成稳定 ID。未来真实 DestinationProvider 应把来源身份下沉到 Provider 契约。
3. 当前候选选择依据能追溯到原有稳定排名，但 DestinationAgent 尚未输出每个候选的分项原始分数；C2 若需要解释目的地初筛，应先扩展真实评分轨迹，不能从排名反推分数。
4. 当前并发上限为进程内 2。接入真实服务后仍需增加 Provider 级限流、熔断、取消与请求级观测。
5. 费用继续使用两位小数归一化的 float；Decimal 迁移仍是后续技术优化。
6. 全部候选、价格、天气、活动时长和强度均为 Mock，不代表真实市场或用户舒适度。
